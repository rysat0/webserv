# 01 HTTPプロトコル — 理解すべきこと(主担当: B、一部共同)

一次情報: RFC 9112(メッセージ構文)、RFC 9110(意味論)、RFC 3986(URI)、RFC 1945(HTTP/1.0)。

---

## H1 メッセージの構造 【B(主)/共, R:M, D:M, ★★★】

**理解すべきこと**
- メッセージ = `start-line CRLF *(field-line CRLF) CRLF [message-body]`(RFC 9112 §2.1)。
- リクエストの start-line は `method SP request-target SP HTTP-version`、レスポンスは `HTTP-version SP status-code SP [reason-phrase]`。
- 改行は CRLF が正だが、受信側は**単独の LF も許容してよい**(§2.2)。ただし CR 単独は不正。許容方針を決める(厳格にして400か、LF許容か)。
- ヘッダー終端(空行 `\r\n\r\n`)の検出方法。TCPは断片で届くため**バッファ内の境界探索**が必要(逐次パース `appendData` 方式の根拠)。
- 行の長さ・ヘッダー総量の上限(§3: 実装側が上限を設けるべき)。上限超過時の 414 / 431 / 400 の使い分け。

**資料化する内容**: パース状態遷移図(PARSING_HEADERS → PARSING_BODY/CHUNKED → COMPLETE/ERROR)、各状態での異常入力と返すコード表。

**調べる時の落とし穴**: 旧RFC(7230)の用語と混在した記事が多い。obs-fold(行折り返し)は9112では**拒否または空白置換**と規定されている。

## H2 リクエスト行・URI・パス処理 【B, R:M, D:M, ★★★】

**理解すべきこと**
- request-target の4形式(origin-form / absolute-form / authority-form / asterisk-form、§3.2)。本課題では **origin-form(`/path?query`)が主**。absolute-form(プロキシ用だが1.1サーバーは受理必須とされる)の扱いを決める。
- `?` で path と query を分離、`#` fragment はサーバーには届かない。
- パーセントデコード(RFC 3986 §2.1)。**デコードのタイミング**(location マッチ前か、ファイルパス結合前か)と、二重デコード禁止。`%00`(NUL)の拒否。
- パス正規化と **ディレクトリトラバーサル対策**(`/../` `%2e%2e` 等)。`root` の外へ出ないことの保証方法。
- メソッド名は大文字小文字区別。未知メソッドは 501、既知だが許可されない場合は 405 — 区別を明確化。
- HTTPバージョン: `HTTP/1.0`, `HTTP/1.1` を受理、`HTTP/2.0` 等は 505。形式不正は 400。

**資料化する内容**: URIの分解手順、正規化アルゴリズム(擬似コード不要・規則の列挙で可)、トラバーサル攻撃のテストパターン一覧。

## H3 ヘッダーフィールド規則 【B, R:M, D:S, ★★★】

**理解すべきこと**
- フィールド名は大小無視(§5.1)、`name:` の直前に空白は不可(あれば400)、値の前後 OWS は除去。
- 重複ヘッダーの結合規則(カンマ区切りで結合可能なもの / `Set-Cookie` のように不可なもの)(RFC 9110 §5.2–5.3)。
- **Host ヘッダー**: HTTP/1.1 では必須。欠落・重複 → 400(RFC 9112 §3.2)。HTTP/1.0 では不要。
- 想定する主なリクエストヘッダー: `Host, Content-Length, Content-Type, Transfer-Encoding, Connection, Expect, Cookie, User-Agent, Accept*`。サーバーが**解釈するもの/無視するもの**の一覧を作る。
- 未知ヘッダーは無視(転送はCGIの `HTTP_*` 用に保持)。

## H4 ボディ長の決定 【B(主)/A, R:L, D:M, ★★★】

**理解すべきこと**(RFC 9112 §6)
- リクエストのボディ長は次の優先順で決まる: `Transfer-Encoding: chunked` → `Content-Length` → ボディなし。**レスポンスと違い、リクエストに「接続を閉じるまで読む」はない**。
- `Transfer-Encoding` と `Content-Length` が**両方**ある場合の規則(スマグリング対策。サーバーは400で拒否するか、TEを優先してCLを破棄)。
- `Content-Length` の検証: 非数字・負数・桁あふれ・**複数値で不一致** → 400。
- `Transfer-Encoding` に chunked 以外(gzip 等)が含まれる → 501。
- ボディ最大サイズ(`client_max_body_size`)の**早期判定**: ヘッダー受信時点で `Content-Length` が超過なら本文を読まず 413 を返せる。chunked は累積で判定。413 返却後の接続の扱い(残りを読み捨てるか閉じるか)。
- POST で Content-Length も chunked も無い場合 → 411(Length Required)か、ボディ0扱いかを決める。
- HEAD/GET のレスポンスと `Content-Length` の関係、1xx/204/304 はボディ禁止(§6.3)。

**重複理解点(A↔B)**: 「リクエスト完了」の判定結果を Client(A)がどう受け取るか(`getState()==COMPLETE`)。パイプライン(1接続で連続リクエスト)を扱わない方針なら、COMPLETE後の余剰バイトの扱いも決める。

## H5 chunked 転送コーディング 【B, R:M, D:M, ★★】

**理解すべきこと**(RFC 9112 §7.1)
- 形式: `chunk-size(16進) [;chunk-ext] CRLF chunk-data CRLF` を繰り返し、`0 CRLF [trailer-section] CRLF` で終端。
- 16進パース(大文字小文字、桁あふれ、空行・不正文字 → 400)。chunk-ext は無視してよい。トレーラーは読み捨て可。
- 逐次パースでの「チャンク境界がrecv断片と一致しない」ケース(サイズ行の途中で途切れる等)の状態設計。
- un-chunk 後のボディを CGI に Content-Length 付きで渡す(課題要件)。
- 累積サイズが上限超過した時点の 413。
- **レスポンス側で chunked を送るか**: 決定事項では `serialize()` で一括生成なので **Content-Length 方式で十分**(chunked送信は不要と判断可。要確認)。

## H6 メソッドの意味 【B, R:M, D:M, ★★★】

| メソッド | 理解すべき点 |
|---|---|
| GET | 安全・冪等。ボディは意味を持たない。静的ファイル/ディレクトリ/CGI |
| HEAD | GETと同じヘッダー、**ボディ無し**(`Content-Length` は GET と同値)。課題必須ではないが実装は容易で、nginx比較・ブラウザ互換で有用。採用可否を決める |
| POST | 非冪等。アップロード/CGI。成功時の `201 Created` + `Location` か `200/204` か |
| DELETE | 冪等。対象はファイルのみか、ディレクトリは?成功時 `204`/`200`、対象なし 404、権限なし 403 |
| 他(PUT/OPTIONS等) | 未実装なら 501(未知)/405(既知だが非許可)。`405` には **`Allow` ヘッダーが必須**(RFC 9110 §15.5.6) |

**資料化する内容**: 「メソッド × 対象種別(ファイル/ディレクトリ/CGI/存在しない) × location設定」のマトリクスと返却ステータス。これがRouter仕様の核になる。

## H7 ステータスコード整理 【B(主)/共, R:L, D:L, ★★★】

決定事項「主要コードを網羅的に実装(基本全部)」に対し、**まず分類して、サーバーが能動的に生成するコードを確定する**ことが必要。RFC 9110 §15 が一次情報。

**作業内容**
1. 全コードの一覧化(1xx/2xx/3xx/4xx/5xx)と reason phrase の表(`HttpResponse` 内 static 表の元データ)。
2. 各コードを3分類: **(a) 本サーバーが生成する (b) 設定次第で生成 (c) 生成しない(プロキシ/キャッシュ/WebDAV専用等)**。
3. 各コードごとに 発生条件・必須/推奨ヘッダー・ボディ有無を記載。
4. 発生モジュールの割り当て(Request/Router/EventLoop/CgiExecutor)。

**想定される主要コード(叩き台)**

| 範囲 | コード | 発生条件の例 | 付随要件 |
|---|---|---|---|
| 1xx | 100 | `Expect: 100-continue` 受信時(任意) | 最終応答とは別に先に送る |
| 2xx | 200, 201, 204 | 成功 / アップロード作成 / DELETE成功 | 201は`Location`推奨、204はボディ禁止 |
| 3xx | 301, 302, 303, 307, 308 | redirect設定、ディレクトリ末尾スラッシュ補完(301) | `Location`必須。301/302とメソッド変更問題、307/308はメソッド維持 |
| 4xx | 400 | 構文不正、Host欠落 | |
| | 403 | 権限なし、autoindex off のディレクトリ | |
| | 404 | 対象なし、locationなし | |
| | 405 | 許可メソッド外 | `Allow`必須 |
| | 408 | リクエスト受信タイムアウト | `Connection: close` |
| | 411, 413, 414, 415, 431 | CL必須/ボディ過大/URI過長/メディア型/ヘッダー過大 | 413のボディ上限は設定値 |
| 5xx | 500 | 内部エラー、CGI異常終了 | |
| | 501 | 未実装メソッド/TE | |
| | 502 | CGI不正出力/起動失敗 | 決定事項: launch失敗→502 |
| | 503 | 過負荷(接続数上限等・任意) | |
| | 504 | CGIタイムアウト | 決定事項: 10秒でkill+504 |
| | 505 | 未対応HTTPバージョン | |

**注意**: エラー応答には `Content-Length` と `Connection: close` を付け、エラーページのボディ(デフォルトHTML生成 / 設定の `error_page` ファイル読み込み)を返す。`error_page` ファイル自体が読めない場合のフォールバック(内蔵HTML)も仕様に含める。

## H8 レスポンスヘッダー 【B, R:M, D:M, ★★】

- 必須/推奨: `Date`(**IMF-fixdate** 形式 `Sun, 06 Nov 1994 08:49:37 GMT`、RFC 9110 §5.6.7。`strftime`+GMT 固定。ロケール依存に注意)、`Server`、`Content-Type`、`Content-Length`、`Connection`。
- 状況別: `Location`(3xx/201)、`Allow`(405/OPTIONS)、`Last-Modified`(静的ファイル。任意)。
- `Content-Type` の charset(`text/html; charset=utf-8` 等)。
- **CGI応答の変換**: CGIの `Status:` ヘッダーからステータス行を作る、`Location:` による リダイレクト(RFC 3875 §6.2)。→ 03 参照。
- HEAD/204/304 のボディ抜き時の `Content-Length` の扱い。

## H9 接続管理 【共, R:M, D:M, ★★】

**理解すべきこと**(RFC 9112 §9)
- HTTP/1.1 は**デフォルトで persistent**、HTTP/1.0 はデフォルトで close(`Connection: keep-alive` で明示)。決定事項は「1.1を名乗りつつ当面 `Connection: close` 固定」→ **仕様上許容されるが、必ず応答に `Connection: close` を付ける**こと。
- `Connection: close` 付きで応答後、サーバー側が close するタイミングと**送信バッファを送り切ってから閉じる**必要(→ 02 N4/N6)。
- keep-alive 対応(後回し)に備えた論点: 1接続で複数リクエスト、`Content-Length` が必須になる、残バイトの持ち越し(パイプライン)、アイドルタイムアウト。
- `Expect: 100-continue`: curl は大きいPOSTで自動付与する(ボディ 1MB 超など)。無視すると約1秒待つ挙動になるため、**対応方針を決める**(100を返す/無視する/417)。
- ブラウザの挙動: 複数接続の並列オープン、空接続(データを送らず接続だけ張る投機接続)がある → 受信タイムアウトとの関係。

## H10 MIMEタイプ 【B, R:S, D:S, ★★】

- 拡張子→Content-Type 表(`.html .css .js .json .txt .png .jpg .gif .svg .ico .pdf .xml` 等)の策定。未知は `application/octet-stream`。
- `Content-Type` が誤ると**ブラウザで表示/DLの挙動が変わる**(課題の「完全な静的サイト配信」に直結)。

## H11 リダイレクト 【B, R:S, D:S, ★★】

- 301(恒久・メソッド変更の曖昧さ)/302/303(GETへ変更)/307/308(メソッド維持)の違い(RFC 9110 §15.4)。設定ディレクティブで**ステータスコードを指定可能にするか**を決める(例: `return 301 /new;` 相当)。
- `Location` は絶対URIでも相対参照でも可(9110 §10.2.2)。ディレクトリへ末尾`/`なしでアクセスしたときの補完リダイレクト(nginxは301)を仕様に含めるか。
